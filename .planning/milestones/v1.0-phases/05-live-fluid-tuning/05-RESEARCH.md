# Phase 5: Live fluid tuning — Research

**Researched:** 2026-09-25
**Requirements:** CTRL-02, CTRL-03, CTRL-04
**Sources:** Current `Shared/` Swift/Metal code, both platform controllers and UI tests, production-state tests, Phase 1 baseline, Phase 3–5 context, Phase 4 UI contract and validation, roadmap and project guidance. Research performed inline because typed `gsd-phase-researcher` dispatch is unavailable in this runtime.

## Planning conclusion

Use the existing bounded `Renderer.state.tuning` as the single source of truth. Make force and dye independent, per-new-input controls; put swirl and retention in the existing per-frame Metal uniform shared by the advection and confinement passes. At defaults the exact values remain force 1, dye 0.8, swirl 0.4, retention 0.998, radius 150 and 40 pressure iterations. Extend the existing native HUD on each platform with a collapsed-by-default Tuning section, four labeled live sliders and percentage readouts; preserve the full-size canvas, HUD positions and input exclusions. A Phase 5 UI-SPEC is required by the enabled UI safety gate before planning layout and interactions in detail.

## Current implementation evidence

- `Shared/SimulationState.swift` already clamps finite force/dye/swirl to 0–2 and retention to 0–1, replaces non-finite values with defaults, and resets tuning to force 1, dye 0.8, swirl 0.4 and retention 0.998. `FluidDynamicsMetalStateTests/SimulationStateTests.swift` covers defaults, bounds, non-finite input and state-only reset. There is no UI-to-renderer tuning setter and none of these values yet affects `Renderer.draw(in:)`.
- `Shared/Renderer.swift` writes up to ten contacts into each `StaticData` buffer via `writeContacts`; it hard-codes scalar impulse `(0.8, 0)` there and passes unscaled contact displacement to `applyForceVector`. Mac contact displacement is generated in `draw(in:)` from `positions`/`directions`; iOS contacts are supplied by `submitTouches()` and queued tap contacts have a zero vector. Sample current tuning when preparing the next running frame, including every contact batch (the extra batch copies the first buffer and calls `writeContacts` again), so a slider change applies to the next movement even in a held stroke. Do not rescale stored GPU slabs or multiply dye by force. A zero-force tap/drag must still produce dye if Dye > 0; zero Dye must still stir if Force > 0.
- `Shared/Shaders.metal`'s `advect` currently multiplies **both** velocity and density by `0.998h`. Its `vorticityConfinement` uses `float2(0.4, 0.4)` for the curl force. Both already receive `BufferData [[buffer(0)]]` through the shared encoder helpers. An aligned appended tuning vector, e.g. Swift `simd_float4` / Metal `float4` with `.x = retention`, `.y = swirl`, permits one per-frame snapshot for both advections and the confinement pass; keep field ordering/stride identical in `StaticData` and `BufferData`. Initialize it for all three in-flight buffers in `initBuffers`, then refresh it in `nextBuffer` each running frame. Metal precision may round 0.998 to half, as it already does; preserve the original effective default by using the same half-precision multiplication semantics. Leave shader entry points, ink radius, pressure iterations and other solver passes unchanged.
- `Renderer.draw(in:)` returns early on pause or inactivity, presents a stored slab and does not call `nextBuffer` or solver passes. Changing tuning while paused should update the in-memory values but must not advance fluid or queue held input; the new values are used on resume. GPU uniform storage is triple-buffered and gated by the existing semaphore; do not mutate a buffer after its command buffer has been scheduled.
- Mac `RenderViewController` has an upper-trailing, material-backed `NSVisualEffectView` HUD, field scroll, Pause/Resume and an `NSEvent` Space/S monitor. Its HUD bounds exclude mouse down from canvas stirring. If a new Tuning button gains focus, add it to the focused-button Space handling so Space activates it once rather than toggling pause. Slider pointer events inside the HUD must not set `mouseHeld` or deposit dye; outside it, existing drag behavior continues.
- iOS `RenderViewController` has a lower-trailing safe-area `UIVisualEffectView`, native buttons and a `UIScrollView` for the field group. `isHUDTouch` filters all canvas recognizers and raw touches; keep its actual HUD bounds as the only exclusion area when expanded. Resizing/rotation already clears/rebases held touches; preserve that contract. A single tap outside the HUD deposits dye through `enqueueTap`, and the existing one-/two-finger double-tap shortcuts must remain unaffected.
- Phase 4 UI tests already launch both app targets and query field selection and pause via accessibility. Reuse the Mac and iOS XCUITest targets for tuning disclosure, slider values and field/pause coexistence; offscreen Metal tests (`test_phase03_metal.swift` and its Python harness) show a precedent for numeric GPU checks but only test resize today. A build or state-only test cannot demonstrate that the GPU actually consumes tuning values.

## Recommended implementation seams

1. **Shared mapping and state:** Define a single pure mapping for four slider positions 0–1 (displayed as rounded 0–100%), their inverse initial positions and endpoint bounds; expose it to both controllers through the shared source already compiled into both targets. A straightforward linear map over the existing bounds is `force = 2p`, `dye = 2p`, `swirl = 2p` (default positions 50%, 40%, 20%). For Fade, choose a narrow useful *retention* window around 0.998 instead of raw 0–1; for example `retention = 0.9995 - 0.009p` yields 0.9995 at 0%, 0.998 at about 16.7%, and 0.9905 at 100%. At 60 running frames, these values retain approximately 97%, 89% and 56% of a stationary signal respectively. The precise range and rounding belong in the UI-SPEC; make endpoints and direction explicit before implementing so both platforms and tests agree. Do not relabel 0% as a claim of zero dissipation; the percentage is position within the chosen useful range.
2. **Renderer/Metal:** Add a narrow `Renderer` tuning mutation API that clamps via `SimulationTuning` and keeps controllers from replacing or separately caching state. At each running `draw(in:)`, apply the force multiplier to contact impulses when writing every batch, set the scalar impulse from `state.tuning.dye`, and pass retention/swirl through matched Swift/Metal uniform data. A force value of zero must not prevent scalar splats; a dye value of zero must not prevent vector splats. Avoid shader behavior changes at the four defaults, and avoid writing to in-flight uniforms when sliders move.
3. **Native HUD extension:** Reuse each existing floating HUD, retain the four named field buttons and Pause/Resume, add Tuning expand/collapse (initially closed) and four native sliders with live percentage readouts. Read actual `renderer.state.tuning` for refresh; don't persist settings across launches and don't add a visible reset yet. Expanded/collapsed state is controller-local, independent of pause, field and canvas contact state. Constrain width and height to the available Mac bounds/iOS safe area and make overflowing content reachable via scroll *inside the HUD*. Avoid nested competing field/tuning scroll gestures at short heights; decide whether to use one bounded combined scroll area while retaining accessible field/pause actions.
4. **Tracer-first execution:** Deliver one Mac path from native slider through shared state and uniforms to observable GPU behavior first, then extend the same mapping/API to iOS and verify both. Preserve and rerun Phase 4 HUD/shortcut tests. Sequence separate UI layout refinements after this first end-to-end user path, not as an isolated horizontal UI-only phase.

## Validation Architecture

| Layer | Command / evidence | What it proves |
|-------|--------------------|----------------|
| Shared mapping and state | `xcodebuild test -project FluidDynamicsMetal.xcodeproj -scheme FluidDynamicsMetalOSX -configuration Debug -destination 'platform=macOS,arch=arm64' CODE_SIGNING_ALLOWED=NO` | Default positions, slider endpoint bounds, Fade inversion and clamping; existing default/reset/field tests still pass. |
| Actual uniform/shader behavior | Build Mac Debug to produce `default.metallib`; extend the existing offscreen Metal harness or add a similarly small GPU test using the freshly built metallib; run it via `python3 -m unittest` for the relevant harness | At defaults, expected scalar/vector impulse and retention/curl behavior; at zero force with dye, dye changes independently; at zero dye with force, velocity changes independently; changing swirl or fade affects nonempty stored fields without fresh contacts. Retention is exercised on both velocity and density. A source-string assertion alone cannot prove these effects. |
| Native HUD regression | Existing Mac and iOS XCUITest `HUDUITests.swift`, plus focused tuning disclosure/value checks on each platform | Fresh-launch closed disclosure, labeled sliders and 0–100% output, field/pause coexistence, control hit-testing and shortcuts. |
| Platform and visual | Build both schemes without deployment overrides; run on an available Mac/iPhone/iPad host | GPU and UI compile; live observation of changed response/fade and default likeness, tapping/dragging outside expanded HUD, scrolling every control in small windows/landscape, pausing and resuming. Distinguish device-only multitouch NOT TESTED from passing automation. |

Sample focused commands after each relevant task rather than a full simulator suite after every change; each completed wave should build both schemes after shared Swift/Metal changes. Create behavior-oriented tests where they can distinguish values actually reaching the GPU from state-only mapping tests. The current production XCTest and UI test targets are already present; no new Xcode test target is needed.

## Planning constraints and open choices

- The Phase 5 CONTEXT decisions D-01–D-10 are locked: one collapsible existing HUD; sticky-open until manually closed; internal scroll in constrained space; per-new-input Force/Dye independence; running-frame Swirl/Fade effects on existing fluid; friendly percentages; Fade increases rightward and crosses the original retention default.
- Phase 6 owns quality/resolution, visible reset and the final accessibility/documentation sign-off; Phase 5 still needs semantic labels and native-operable controls for its own interactions.
- The Phase 4 UI contract establishes the baseline material, inset, field/pause labels and native input exclusion. A Phase 5 UI-SPEC must settle slider dimensions, disclosure placement, small-window scrolling and Fade endpoint/percentage copy before planning passes the UI gate.
- `.planning/config.json` and some Phase 4 files are already modified in the workspace. Keep Phase 5 research/planning isolated; do not overwrite those in-progress changes.
