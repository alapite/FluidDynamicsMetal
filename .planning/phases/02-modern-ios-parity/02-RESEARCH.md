# Phase 2 — Modern iOS parity research

**Researched:** 2026-09-24
**Question:** What must be understood to plan a current-Xcode iOS 26 app with the Mac fluid baseline and reliable simultaneous touch interaction?

## Scope and sources

Source of truth: `02-CONTEXT.md` (D-01–D-11), `ROADMAP.md` Phase 2, `REQUIREMENTS.md` (PLAT-02, PLAT-03, SIM-01), `01-BASELINE.md`, `README.md`, the Xcode project, both controllers, `Shared/Renderer.swift` and `Shared/Shaders.metal`. Local environment: Xcode 27.0 (27A266a) and available iOS 26.3 / 26.4 iPhone and iPad simulators (`xcrun simctl list devices available`). The project has no test target. Phase 1 already builds the Mac target at macOS 26.0 / Swift 5.0; its actual macOS 26 runtime check remains deferred to milestone closeout.

## Build and integration facts

- `FluidDynamicsMetal.xcodeproj/project.pbxproj` has `IPHONEOS_DEPLOYMENT_TARGET = 10.3` and `SWIFT_VERSION = 4.0` at project Debug/Release, plus iOS target `IPHONEOS_DEPLOYMENT_TARGET = 10.0`, `SWIFT_VERSION = 4.0`, and `SWIFT_SWIFT3_OBJC_INFERENCE = Default` in both configurations. Update project and iOS target settings to iOS 26.0 / Swift 5.0, remove obsolete Swift 3 inference and armv7-only `UIRequiredDeviceCapabilities` in `FluidDynamicsMetaliOS/Info.plist` (use `metal` if a capability is needed). Leave the already modern Mac target at macOS 26.0 / Swift 5.0. Run both schemes without deployment-target command-line overrides and `CODE_SIGNING_ALLOWED=NO`; for iOS specify `-destination 'platform=iOS Simulator,name=iPhone 17 Pro,OS=26.4'` or an installed exact simulator ID. The iOS app bundle's `MinimumOSVersion` must read `26.0` and contain `default.metallib` before treating a successful compile as a usable app.
- Both targets compile the same `Shared/` Swift and `Shaders.metal` sources directly. Changing Swift `StaticData` fields or capacity also requires a matching Metal `BufferData` update and a Mac rebuild; shader names are runtime string lookups. Do not alter the 40 pressure iterations, density initial display, visualization RGB `(0.0, 0.06, 0.19)`, advection factor `0.998h`, curl `(0.4, 0.4)`, or the Mac baseline's `inkRadius=150` and scalar impulse `(0.8, 0.0)`.
- `FluidDynamicsMetaliOS/Base.lproj/Main.storyboard` already has a full-root `MTKView` and `multipleTouchEnabled="YES"`. `isExclusiveTouch = true` on the iOS view means it should be checked when implementing simultaneous touch; retain a full unobstructed canvas and hidden status bar.

## Input and GPU contract

- iOS `touchesBegan` and `touchesMoved` currently use only `touches` (the *changed* set), do raw `malloc`/`memcpy` into a five-position tuple without freeing it, and do not cap the copy to five entries. A sixth touch risks writing beyond the allocation. Every end/cancel currently forwards `nil`, cancelling all active fingers (D-01/D-02). Use a tracked identity-to-position map (`UITouch` identity) with stable slot ordering and forward the complete active set after each change; remove only ended/cancelled identities. Use `touch.location(in: metalView)` so the coordinates and `view.bounds` agree. Avoid the raw allocation.
- `Renderer.updateInteraction` only sets `positions`; `draw(in:)` retains `directions` from the prior frame and `nextBuffer` does not clear positions/impulses on nil input. On release/restart or when fingers change, stale GPU splats or large artificial impulses can appear. Ensure each active contact has a previous position initialized to its own current position; a new finger must not inherit another finger's slot history. Explicitly write zeroed position/impulse uniforms and scalar impulse for empty input. Force while dragging must apply on the first moved frame; stationary contact deposits dye without an artificial vector impulse.
- `StaticData` has five `float2` contacts and `BufferData` loops over 5; the phase's every-active-finger requirement needs a capacity strategy for the supported multi-touch hardware (up to ten simultaneous iPad contacts). A fixed ten-slot Swift tuple/Metal array with identical stride and index mapping is a contained approach; when implementing, verify Swift and Metal offsets and test five-plus contact transitions. Alternatively batch splats into multiple force passes if a device exceeds the chosen capacity; never silently drop live touches or overflow a tuple. Slots must be stable across frames; `Set<UITouch>` iteration order is not stable.
- The shader's `gaussSplat(coords, radius)` computes `exp(-dot(coords,coords)/radius)`: `inkRadius` is a squared-distance denominator, **not** a linear pixel radius. The renderer uses view points (`view.bounds`) for simulation textures, not `drawableSize` pixels. For an iOS-only same-proportion footprint, scale the denominator approximately as `150 * pow(min(view.bounds.width,view.bounds.height)/375, 2)` so a 375-point-wide phone retains the reference footprint and iPad scale grows proportionally (D-07). Retain the Mac's 150. Keep orientation/resize resilience itself for Phase 3.

## Gesture arbitration

- The existing one-finger and two-finger double-tap recognizers invoke `doubleTap()` and `changeSource()`, respectively. Forwarding every touch-down directly can write a dye splat before a double-tap is recognized; clearing GPU state afterwards cannot erase dye already written (D-05). Design the input gate so an ambiguous stationary touch is pending, not injected; use tap recognizer failure relationships / recognized shortcut cancellation to distinguish single-tap dye from either double-tap, with prompt drag forwarding after movement. A deferred single-tap recognizer requiring both double-tap recognizers to fail can inject a tap on completion; a short hold/stationary path should also emit dye after the gesture ambiguity resolves. Verify that a two-finger double tap causes *one* field cycle and no splat, and that two active drags retain independent positions when one lifts. Avoid delaying a real drag for the double-tap window.
- D-04 preserves Mac Space and S and iOS two shortcuts. Do not replace the gestures with named controls (Phase 4), or pull Phase 3 pause/rotation work into this slice.

## Suggested vertical execution slices

1. Bring the iOS target to iOS 26 / Swift 5 with a runnable iPhone simulator Metal app and a clean Mac rebuild; preserve original input and rendering as the tracer slice (PLAT-02, PLAT-03, SIM-01).
2. Implement stable multi-contact transport and clean gesture arbitration in the controller and renderer while retaining the Mac input and GPU defaults; verify with iPhone and iPad simulator flows and record untestable physical multi-finger behavior honestly (SIM-01, D-01–D-07).
3. Record observed iPhone/iPad launch, drag, shortcuts, black/blue default and Mac parity evidence with PASS/FAIL/NOT TESTED in a phase-local verification note (D-09–D-11). The simulator cannot by itself establish physical-device support.

## Validation Architecture

- Automated quick gate: Xcode Debug iOS Simulator build (`-project FluidDynamicsMetal.xcodeproj -scheme FluidDynamicsMetaliOS -configuration Debug -destination 'platform=iOS Simulator,name=iPhone 17 Pro,OS=26.4' CODE_SIGNING_ALLOWED=NO build`) after code changes. Also build `FluidDynamicsMetalOSX` for `platform=macOS,arch=arm64` without deployment override after any `Shared/` change. Check effective iOS build settings with `xcodebuild ... -showBuildSettings`, the built bundle's `MinimumOSVersion` using `PlistBuddy`, and `default.metallib` existence. Build checks do not prove runtime dye/gesture behavior.
- Full gate: both no-override builds plus launch of installed app in iOS 26 simulator on iPhone and iPad (`xcrun simctl boot`, `bootstatus`, `install`, `launch`; capture errors and avoid stale product), followed by visible drag, single stationary tap, double-tap shortcuts and dye-free shortcuts. Single-pointer simulator input does not establish all multi-touch edge cases; verify repeatability with unit/UI checks if a small harness can be added without destabilizing this no-test-target project, otherwise record multi-touch as unverified/device-only (D-11).
- Manual Mac check uses `01-BASELINE.md`'s already-observed macOS 27 drag/Space/S reference and a fresh Mac rebuild; do not claim macOS 26 runtime pass. On iPhone and iPad confirm unobstructed black canvas, initial density, blue dye, swirl/fade, gesture field order; record host/runtime and explicit observations in a Phase 2 note, with `NOT TESTED` for unreachable physical multi-touch. No screenshot requirement.

## Risks / deferred

- Input tracking and rendering access occur on UIKit and `MTKView` callback paths; preserve coherent snapshots across frames. A stale previous position or uncleared uniform creates false velocity/dye; a recognizer can deliver began before it recognizes the second tap. Observe actual gesture timing in simulator before claiming D-05.
- iOS 26 simulator Metal availability and runtime performance must be checked after build. Codesigning-disabled simulator builds are not evidence of installation on a physical iPhone/iPad; D-09 defines simulator sign-off for this phase.
- Phase 3 owns robust resize/rotation and pause state; Phase 4 owns named controls. Phase 1 macOS 26 runtime remains the milestone-closeout check.
